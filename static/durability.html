Recorded durability test

The alert survives a crash

Baridi drives its breach alert with Temporal. To check that the alert is not lost when a process dies, we killed a worker in the middle of sending an alert and watched Temporal resume the work on a new worker. This page shows that captured run.

Recorded, not live This is a captured run from the build instance, kept here as a record. It is not a live action and nothing on this page starts a worker. No live Temporal server runs on the web path, and port 7233 stays off in production.
Kill and resume, fridge-01 2026-10-12 Late, not lost

A worker dies mid-alert and the alert still fires once

Worker A ran with a 25 second delay inside the alert step, so it could be killed after the breach was known but before the alert was durably written. The breach count was already decided. Only the write had not happened yet.

final alert count: 2, none lost, none doubled, about 31 seconds late.

The alert fired late because Temporal retried after the worker died. It was not lost, and it did not double-fire. The two keys below are the final lines in the alert log, one for each excursion on the featured day.

Why this matters

The durability mechanism is Temporal. It checkpoints the workflow, so a crash resumes from the last step instead of dropping the alert. That is the same thing the home page calls an alert that survives a crash, shown here as a recorded kill-and-resume rather than words. On the live site the breach timeline is served by the read-only API and TimescaleDB. The worker in this test is a separate process and does not run on the web path.
